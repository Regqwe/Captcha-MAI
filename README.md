# Captcha-MAI — финальная PP-OCRv6 small

В проекте одна модель, один ноутбук и одна точка запуска.
Единственная ветка — `codex/initial-experiments`.

**PP-OCRv6 small**, CPU, распознавание строки и наблюдение за Android через ADB.
Область строки задаётся профилем экрана и проверяется по элементам интерфейса. Детектор текста,
другие модели, Gemini, платные API, архивы и старые экспериментальные ноутбуки
удалены из текущего дерева. Размеченная выборка уже лежит обычными изображениями.

Подтверждённая точность: **1876/1984 = 94,56%** на публичном holdout.
На семи визуально размеченных целевых изображениях — **4/7**. Этого недостаточно,
чтобы обещать качество на реальном потоке; [ограничения ниже](#качество-и-ограничения).

## Запуск

Windows, Python 3.12. Из корня репозитория:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -X utf8 scripts/run.py review
```

Просмотр результатов не загружает модель. Для нового полного локального прогона:

`benchmark` — отдельная исследовательская команда: повторно проверяет точность
и скорость на размеченных изображениях. Для работы с телефоном она не нужна.
`review` только читает сохранённые ответы и строит сводку.

```powershell
.\.venv\Scripts\python.exe -X utf8 scripts/run.py benchmark
```

Команда проверяет SHA-256 изображений, выполняет единственный ноутбук настоящим
inference и обновляет его выводы и `research/results/`. Ядро Jupyter выбирается
автоматически из текущего Python. Первый запуск скачивает только публичные веса
распознавателя, около 21 МБ; их контрольная сумма закреплена в `research/model.json`.

Распознать свою **вырезанную область с символами**:

```powershell
.\.venv\Scripts\python.exe -X utf8 scripts/run.py predict path/to/crop.png
```

## Телефон через ADB

Перенесена и исправлена логика из [папки с исходниками](https://drive.google.com/drive/folders/1QQL9mCoTOBEysxFbRe2V1eLz_rij1iwx).
В `phone_bot.py` был отдельный PaddleOCR, обрезка правых 28% изображения,
удаление всех букв и запасные нажатия по фиксированным координатам.
`test_single_image.py` импортировал отсутствующую функцию; `test_local.py`
называл успешным результат нужной длины без сравнения с меткой.
Новый контур использует ту же PP-OCRv6 small, что и финальный benchmark.
Исходное виртуальное окружение, старые архивы, Gemini и шесть прежних ноутбуков
из Drive в рабочий проект не возвращались.

Включите отладку по USB и подтвердите подключение на телефоне. Подключение и
чтение экрана проверены на настоящем Android 22 октября 2026 года, 1080×2400.
ADB доступен через Windows-пакет `adbutils`; отдельный Android Studio не нужен.
Если ваш ADB не запускается, официальный источник —
[Android SDK Platform-Tools](https://developer.android.com/tools/releases/platform-tools).
При первом подключении [uiautomator2](https://github.com/openatx/uiautomator2)
запускает вспомогательный сервис на телефоне.

```powershell
# Проверить, что телефон виден и имеет состояние device
.\.venv\Scripts\python.exe -X utf8 scripts/run.py phone-check

# Сохранить настоящий экран и дерево интерфейса локально в runs/capture
.\.venv\Scripts\python.exe -X utf8 scripts/run.py phone-capture

# Только наблюдать, без ввода и нажатий, 60 секунд
.\.venv\Scripts\python.exe -X utf8 scripts/run.py phone --observe --duration 60

# Непрерывно распознавать и отправлять поддерживаемые капчи; Ctrl+C останавливает
.\.venv\Scripts\python.exe -X utf8 scripts/run.py phone
```

При нескольких устройствах добавьте `--serial СЕРИЙНЫЙ_НОМЕР`.
Одна итерация: UI XML и снимок → проверка заголовка, подсказки и геометрии →
вырезка полной строки → два стабильных кадра → локальное распознавание →
проверка формата и score → повторное чтение экрана → ввод через найденный
EditText → проверка введённого текста → нажатие актуальной кнопки Next/Далее.
Нет нажатий наугад, клавиши Back и промежуточных картинок в корне проекта.

`phone-profile.json` рассчитан на показанный в Drive портретный экран
«Confirm you're human»: шесть цифр, ROI `[0.10,0.23,0.90,0.35]`.
Это профиль конкретной вёрстки, а не универсальный детектор любой капчи.
При другой вёрстке сохраните экран, проверьте область и измените `roi`.
`title`, `footer`, `input`, `submit`, `refresh` — регулярные выражения для UI.
Можно закрепить `package` за приложением; `null` допускает приложения с подходящим UI.
Если WebView не отдаёт элементы, скрипт сообщает об этом и ничего не нажимает.

Для воспроизводимой проверки есть [демоформа 2Captcha](https://2captcha.com/demo/normal).
Откройте её в Chrome на телефоне и используйте отдельный профиль:

```powershell
.\.venv\Scripts\python.exe -X utf8 scripts/run.py phone --profile phone-profile-demo.json
```

Демопрофиль проверен на подключённом телефоне 1080×2400, при указанной
в профиле позиции страницы. Локальная модель прочитала `W9H5K`, скрипт ввёл
ответ, нажал Check и сам обнаружил сообщение `Captcha is passed successfully!`.
В последнем прогоне была одна отправка, статус `accepted` получен примерно
через 9 секунд после начала наблюдения. Платный API 2Captcha не используется.
Одна и та же статическая картинка проверена дважды; это проверка взаимодействия
с телефоном и формой, а не новая независимая оценка точности модели.

Для пяти букв/цифр, как в приложенной вырезке `W9H5K`, задайте
`"code_pattern": "[A-Z0-9]{5}"` в копии профиля и передайте `--profile путь.json`.
Буквы, регистр и ведущие нули сохраняются; шум не превращается в допустимый
ответ удалением символов. `min_score` по умолчанию 0,90 — настраиваемый фильтр,
а не доказанная вероятность правильного ответа.

Одна картинка повторно не отправляется в пределах текущего экрана. Не более
трёх действий отправки/обновления за непрерывный эпизод; смена картинки не
сбрасывает лимит. При неподходящем распознавании обновление возможно только
через однозначно найденную кнопку «Get a new code». Если кнопки нет, скрипт ждёт.
Ожидание ответа — 12 секунд; повторная отправка того же ответа запрещена.
Исчезновение капчи записывается как `screen_left_unverified`, **не как успех**:
приём ответа требует отдельного признака результата. Необязательное поле
`success` задаёт такой признак: в демопрофиле это точный текст успешной проверки.
Статус `accepted` возникает только после собственной отправки; уже открытое
сообщение об успехе обозначается `already_accepted`.
После трёх последовательных ошибок связи наблюдение останавливается.

Журналы содержат локальные ответы и находятся в игнорируемой Git папке `runs/`.
Используется стандартный Python `logging`. В консоли — время UTC, уровень,
имя компонента и сообщение; в файлах — UTF-8 JSONL с отдельными полями
`time`, `level`, `logger`, `message`, `status` и данными события.
Исключения сохраняются с полным traceback. `INFO` показывает основные действия,
`WARNING` — отклонённый ответ/лимиты, `ERROR` — сбои; `DEBUG` дополнительно
показывает чтение экрана, промежуточные состояния и время распознавания.

```powershell
.\.venv\Scripts\python.exe -X utf8 scripts/run.py phone --profile phone-profile-demo.json --log-level DEBUG
.\.venv\Scripts\python.exe -X utf8 scripts/run.py phone-check --log-file runs/custom.jsonl
```

Общий журнал всех команд — `runs/app.jsonl`; сменить его можно `--log-file`.
Журнал сеанса телефона — `runs/<дата-время>/events.jsonl`, либо в папке `--output`.
Отдельный процесс Jupyter пишет прогресс benchmark в `runs/benchmark.jsonl`.
Уровень меняется через `--log-level DEBUG|INFO|WARNING|ERROR` до или после команды.
Каждый файл ротируется при достижении 5 МиБ, сохраняются три предыдущих файла
с суффиксами `.1`, `.2`, `.3`. Папки старых сеансов автоматически не удаляются.

Снимки рабочего стола подключённого телефона в репозиторий не публикуются.
Связь, чтение, ввод, нажатие и успешная проверка демоформы подтверждены
на настоящем телефоне. Прохождение капчи в целевом приложении из исходного
задания ещё не проверено. Проверки с синтетическим XML в `tests/` проверяют
логику, а не точность OCR или приём ответа внешним сервисом.
В проверке на рабочем столе телефона получены 5 кадров без ошибок,
медиана итерации 2,33 секунды плюс пауза опроса 1 секунду.
Это периодическое чтение экрана, не видеопоток; 25 мс локального OCR не равны
задержке всего контура. Протокол — `research/results/adb-validation.json`.

Настоящие примеры из Drive с отдельными визуальными метками сохранены в
`datasets/phone/labels.csv`. Повторить реальное распознавание:

```powershell
.\.venv\Scripts\python.exe -X utf8 scripts/run.py phone-eval
```

Получены `558796` из полного экрана и `W9H5K` из вырезки, **2/2**;
ответы, SHA-256 и время — `research/results/phone.json`. Метки прочитаны
ассистентом, набор использован при разработке. Два примера не заменяют
независимую оценку точности и не входят в исходный holdout.

## Состав

- `notebooks/final_ppocr_small.ipynb` — единственный рабочий ноутбук.
- `captcha_lab/model.py` — только PP-OCRv6 small, ONNX Runtime на CPU.
- `captcha_lab/evaluation.py` — реальный прогон, exact match, CER и Wilson CI.
- `captcha_lab/phone.py` — разбор UI, стабильность кадров и ограничение попыток.
- `captcha_lab/android.py` — подключение, чтение экрана, ввод и наблюдение.
- `captcha_lab/logging_config.py` — консоль, JSONL, уровни и ротация журналов.
- `phone-profile.json` — формат ответа и геометрия конкретного экрана.
- `scripts/run.py` — единая точка запуска оценки, распознавания и ADB.
- `datasets/holdout/` — 1984 настоящих изображения с метками и SHA-256.
- `datasets/target/` — 9 целевых вырезок: 7 читаемых и 2 спорных.
- `datasets/phone/` — 2 размеченных примера из дополнения Drive.
- `research/results/` — ответы, эталоны, задержки и параметры единственной модели.
- `research/comparison.csv` — сохранённое сравнение, по которому выбрана small;
  это история исследования, а не дополнительные исполняемые модели.
- `tests/` — проверки метрик и целостности данных.

Прямые зависимости закреплены в `requirements.txt`; точный состав проверенного
Windows-окружения — в `requirements-lock.txt`. PyTorch и альтернативные OCR-пакеты
не нужны. Тесты: `python -m unittest discover -s tests -v`.

Старое полное исследование пяти моделей и исторического Gemini сохранено в
[истории Git](https://github.com/Regqwe/Captcha-MAI/tree/43737f7).
Обучение и подстройка preprocessing на holdout не выполнялись. ADB реализован;
полный автоматический поиск области произвольной капчи и подтверждение приёма
ответа сторонним сервисом не доказаны.

## Качество и ограничения

Финальный ноутбук выполнен на настоящих изображениях: 1876/1984 правильных строк,
exact match 94,56%, Wilson 95% CI 93,47–95,47%, CER около 1,02%.
В последнем прогоне медиана 25,4 мс на изображение на CPU; текущие значения —
в `research/results/summary.csv`, версии и параметры — в `research/results/run.json`.
Время включает открытие файла, preprocessing, inference и decoding; загрузка и
прогрев белым изображением учитываются отдельно.

Target даёт 4/7 с широким 95% CI 25,05–84,18%. Семь меток визуально прочитаны
ассистентом, два случая спорные и исключены из знаменателя. Это development-набор,
ранее использованный при исследовании, а не независимая production-проверка.
Нельзя обещать качество на реальном потоке по этому результату. Ошибки и пустые
ответы входят в знаменатель; ведущие нули сохраняются строками.

В сохранённом сравнении на одинаковом holdout small имела 94,56%, ddddocr beta —
73,84%, tiny — 49,09%, Conv-Transformer — 44,41%, CRNN — 33,52%.
Поэтому оставлена small. Полные данные сравнения — `research/comparison.csv`;
снятый код и подробное исследование доступны в указанном выше коммите Git.
Исторические сетевые отказы Gemini не доказывают качество самой VLM;
новые вызовы отменены, платного клиента в проекте нет.

## Данные и происхождение

В `datasets/holdout/images/` находятся 1984 настоящих JPG из test-части
[project-sloth/captcha-images](https://huggingface.co/datasets/project-sloth/captcha-images),
ревизия `eeaf2b6ec9086645f270f7e2aaa9ea90730683de`. Карточка источника заявляет WTFPL.
Метка — шестизначный префикс исходного имени. 16 ранее просмотренных изображений
исключены; перечень — `datasets/holdout/excluded.csv`. Обучающих архивов в проекте нет.
`datasets/audit.json` хранит аудит исходного корпуса и SHA-256 текущего манифеста.
Перед benchmark проверяется SHA-256 всех 1993 проверочных картинок.

В `datasets/target/` находятся 9 вырезок из предоставленных пользователем экранов.
Область вручную выбрана на исходном размере 1080×2220 по нормированным координатам
(0.10, 0.24, 0.93, 0.36). Метки, спорные кандидаты и хеши — в `annotations.csv`.
Полные исходные экраны не публикуются. Неизвестно, входил ли публичный корпус
в обучение авторов готовых весов.

## Модель и источники

Путь данных: вырезанное RGB-изображение → BGR-вход RapidOCR → LCNetV4 + LightSVTR
→ CTC → строка. Детектор и классификатор ориентации отключены; вспомогательная
обучающая NRTR-ветвь при inference не запускается. Принцип CTC сохраняет порядок
символов без разметки их границ. Веса загружаются публично и отдельно от проекта;
их SHA-256 и размер закреплены в `research/model.json`.

- [PP-OCRv6](https://arxiv.org/abs/2606.13108) — структура recognizer и отличия small/tiny.
- [Model card small](https://huggingface.co/PaddlePaddle/PP-OCRv6_small_rec_safetensors).
- [CTC, Graves et al., 2006](https://www.cs.toronto.edu/~graves/icml_2006.pdf) — выравнивание последовательностей.
- [Ye et al., CCS 2018](https://eprints.whiterose.ac.uk/id/eprint/151526/1/ccs18.pdf) — адаптация к конкретному семейству капч.

В runtime используются RapidOCR и ONNX Runtime; веса в репозитории не
распространяются. Распознаваемое изображение передаётся только локальной модели.
